# Learning Log

## 1. Sprint Planning and Requirements Selection
We picked "one allergy order goes from the table to the kitchen and back" as our sprint scenario, which includes 2 screens: the server's tablet and the kitchen's order display.  We chose it for the following reasons. First, it is core because the whole system is mainly about carrying a guest's allergy to the kitchen, and all three of our models break the main goal (G-2) into the same steps. Second, it is user-facing because Kayla uses the tablet and the kitchen uses the display to deal with allergens, and these two devices are invloved in our sprint scenario. Third, it is uncertain because we did not know if our goals really help them. For example, we did not know if a "Not confirmed" label still help Kayla. So building it first tells us more unknown information, which we can improve in later versions.

Also, we left some goals out of the sprint for the following reasons. First, changes after the order is sent are important, but they need an order to exist first. Second, updating the dish records happens in the back office not in the kitchen or table, so mock records should stand for it in the case. Third, the guest menu app is a different user and a different screen other than the serer's tablet or the display in the kitchen.

We merged our three models from 231 goals to 88 goals at first. Then we narrowed down the goals in this flow into 22 requirements, with 17 MUST and 5 SHOULD requirements. MUST is what the round trip cannot work without. SHOULD are the ones that make it better.

The goal model mainly helped us in three ways. First, it showed overlaps, so we which goalsare the same and should be merged into one (for example, G-10, the allergy attached to the seat). Second, the refinements showed the order of the steps, so it help us wrote them as dependencies D-1 to D-6 more easily. Third, the conflict links showed which goals pull against each other. For example, Kayla wants a "safe" label, but Sofia says nothing is safe until the kitchen checks it (C-1). So we never show "safe", but only "Contains" or "Not confirmed". Finally, we decided six of the eight conflicts in the sprint for V1. C-5 and C-7 stay unresolved, because we need more information to secure these decisions, it's better to choose a safer approach at the time. So for now, we picked the safer choices.

## 3. Revisions and Learning
We found four problems in our v1 model. All of them were requirements issues. So we changed the spec and the goal model first, and then updated the code.

1. Traces should be shown in kitchen(REQ-06, G-30). 
In V1, the server recorded whether traces matter, but only the tablet showed it. However, the kitchen is the one that handles most of the cross stage communication, so it needs the trace of order the most. Now each allergy item on the kitchen ticket shows “Traces: yes” or “Traces: no”. So Sofia’s trace setting now reaches the people who cook her food.

2. The kitchen should not confirm a dish with the customer's allergen (REQ-10, new G-89).
In V1, the server could send a dish that shows “Contains”, and we thought the kitchen review would catch it. But in some cases, it did not. For example, a walnut salad for a customer with a tree-nut allergy was confirmed and reached “OK to serve”. Now the kitchen cannot tap “Confirm” on a dish that lists the customer’s allergen. It can only tap “Cannot confirm”. So the safety rule is now built into the system, and it is more likely to work when the kitchen is busy. Because the kitchen cannot tap “Confirm” by accident anymore, so the wrong food will not be served if the server accidently send a order with allergen to the kitchen, and the kitchen does not check it before pressing "confirm".

3. The server should be able to use a chef-approved change (REQ-20, G-25).
In V1, this was SHOULD, and the tablet only listed the chef-approved changes. For example, for a walnut salad and a guest with a tree-nut allergy, the tablet showed "Without walnuts" as text. So the server in fact could not pick one because it was SHOULD, and the kitchen never saw it. So, it made it seem like a meaningless feature. Now REQ-20 is MUST. The server picks one change approved by the chef, like "Without walnuts", and the kitchen ticket shows it. But the kitchen still cannot confirm the dish, because the dish record only says the change is approved. It does not say the change removes the allergen for the specific customer. For example, the salad may still touch the same cutting board, or the dressing may have nuts. We chose this small version on purpose, because a bigger one would weaken change 2. And it's safer to do this way. And we keep it as a new unresolved conflict, C-12.

4. The allergy ticket should stay on top after “Acknowledge” (REQ-08, G-32).
In V1, the allergy ticket stayed on top only until someone acknowledged it. After that, it dropped back among the normal ticket. However, acknowledge can only indicate that the kitchen saw the ticket, it does not imply that the allergen is solved. We still need it to be confirmed or not-confirmed, then be sign-off by the expediter. So, this could made the ticket with allergen accidently be pushed down to the bottom and mixed with the other ordinary tickets. In the interview, Antoine said to keep it prominent until the expediter acts on it, and the expediter acts at sigh-off station. So originally we read him too narrowly. And moreover, this could lead to our concern in the goal model (O-1: AllergyTicketMissedOrClearedDuringRush) the allergen could be unsolved when the kitchen is rush or busy. Now the ticket stays above normal tickets until every allergy is signed off or marked “Cannot confirm”. So the kitchen can find it easily for the whole review, not only at the start.

### Prototype changes

For each change, we updated the spec first, then the plan and tasks (Phase 11 of `tasks.md`), then wrote failing tests, then changed the code. V1 is commit `53c5965` and V2 is the `v2` tag. The numbers follow the list above.

1. **Traces (REQ-06, observation O-02).** The trace setting was already stored in the allergy snapshot, but `kitchenItemText` never printed it. It now adds "Traces: yes" or "Traces: no" after the severity, using the same `tracesLabel` helper as the tablet, so both screens use the same words. If a seat's allergies disagree, I chose "yes", the stricter reading.

2. **No "Confirm" for a listed allergen (REQ-10, observation O-01).** `offeredActions` no longer offers "Confirm" when the dish lists an allergen from the snapshot taken at send. The `confirm` reducer re-checks `offeredActions`, so a stale tap on an old button does nothing. I used the snapshot, not the seat's current allergies, because that is what the kitchen sees. I also counted every severity, because the stricter reading only matters on a seat that is already an allergy order. A round-trip test checks SC-008.

3. **Chef-approved change (REQ-20, observation O-04).** Order items have a new `pickedChange` field. On a draft item that shows "Contains", the server taps one approved change, and tapping it again clears it. Both screens show "Chef-approved change: <text>". `pickChange` only accepts text from the chef's list, and `sendOrder` drops a change that no longer applies, for example if the allergy was removed before sending. Because the data shape changed, `schemaVersion` went to 2, so a tab still holding V1 data reloads fresh data instead of breaking. A test checks that a picked change does not bring "Confirm" back (C-12).

4. **Ticket order (REQ-08).** `sortTickets` now has three ranks: not acknowledged, acknowledged with an open allergy item, and everything else. An item is open until it is signed off or marked "Cannot confirm". I did not add a label for the middle rank, because the spec does not name one and each item already shows its own status.

**How I checked it.** All V1 tests still pass except the two that asserted the old behaviour (the ticket dropping back after "Acknowledge", and REQ-20 as text only), which commit `eaea1f2` replaces. The suite went from 202 to 241 tests, and lint and build pass. I then did the two-tab walkthrough from `quickstart.md` on the V2 URL. V1 and V2 stay on separate URLs, so they can be compared side by side.

### Reflection
**1. Which decisions required your judgment rather than relying solely on AI?** 
When we were working on our v2 update, we decided whether to make it available for the server to use the chef's approved change for the allergen when ordering. We decided whether to let the server use it and not modify the procedure after that (fully trust this approval) or whether we should have a guard; we decided we should not fully trust it cause, it does not guarantee that other allergens outside the approval are satisfied
**2. How did prototyping change your understanding of stakeholder needs?** 
It helped us understand that we can't fully satisfy all three stakeholders' needs. Because some of them are actually in conflict with each other. So, in the process, we went back to the transcript and evaluated the stakeholders' needs and priorities. For example, in C-2, the customer wants every single detail of their allergen to be recorded; however, the server wants to avoid complicated typing. In this case, we have to go back to the transcript to analyze it more deeply and understand what the stakeholders really mean; they might have priorities. Like here, actually, the server's priority is not that she does not want to record the details, but she does not want the recording to slow her down when ordering. 
**3. How did spec-driven development help maintain consistency between the requirements and implementation?**
In the spec, we wrote the requirements in detail, including test cases and different scenarios. And we use this spec to develop the code, so when we implement, we can use the exact scenario to check, since it's documented. And we can do this by elevating a structure, versioned specification into the single source of truth that directly drives code generation and automated verification
 **4. What evidence from your work would you present to management to demonstrate the value you contributed beyond AI-generated specifications and code?**
